## LINE 圖片下單 + 社群連線訂單 (new feature, this round — not yet usable end-to-end)

A brand-new, fully independent feature: customers order by sending photos of products directly to the LINE Official Account chat, no website involved. Does **not** touch `community_orders`/`community_order_items`/the existing 記事本 system in any way, and does **not** change the existing admin-approval binding review page/API (`社群名單` tab, `/api/backend/community/members`) — this round only adds a *customer-facing, self-service* path that writes into the same `community_line_bindings` table using columns that page already reads.

### Not usable yet — 3 manual setup steps required

1. **Apply the 2 new migrations to Staging** (see below) — nothing in this feature works at all until they're applied (every route degrades to a DB error, not a silent no-op, since these are brand-new tables/bucket with no fallback).

3. **Register the webhook URL in the LINE Developers console**: `https://pinkkkuin-staging.vercel.app/api/line/webhook`, on the same Messaging API channel `LINE_CHANNEL_ACCESS_TOKEN`/`LINE_CHANNEL_SECRET` already belong to (the one push notifications already use). Also recommended: configure a Rich Menu with a "我要下單" button — either a `message` action that sends the literal text "我要下單", or a `postback` action (both are matched the same way, see below) — LINE Rich Menu configuration itself is outside this codebase, done in the LINE console/API directly.

Confirmed via `curl -X POST https://pinkkkuin-staging.vercel.app/api/line/webhook`: returns `401` (not `404`), meaning `isLineWebhookConfigured()` already finds `LINE_CHANNEL_SECRET` and the signature check correctly rejects an unsigned test request — the route itself is live, just untested end-to-end (needs a real signed request from LINE, i.e. step 3 above).

### ⚠️ Rich Menu — do not publish to all friends yet

This is a **real** LINE Official Account with **1,546 existing friends**. The new "我要下單" Rich Menu must **not** be set as the account's default/全體 menu until testing is done — every one of those friends would immediately see and be able to trigger the new ordering flow.

### 功能一：LINE 帳號綁定（自助式）

- `src/lib/line/livestream-orders.ts::handleTextMessage` — on any text message from a user with no binding row (or `review_status` other than `pending`/`approved`), matching one of `ORDER_TRIGGER_KEYWORDS` (`我要下單`/`下單`/`開始下單`/`開通`/`綁定`/`加入社群`/`註冊`, loose substring match) sets `community_line_bot_states.awaiting_nickname = true` and replies asking for the nickname. The very next text message from that user (regardless of content) is read as the nickname, not matched against any keyword.
- Nickname submission: checks for a collision against **already-approved** bindings only (`ilike` on `nickname`, excluding this same `line_user_id` — the exact same rule `src/app/api/backend/community/members/route.ts::validateNickname` already uses for the admin-approval flow), replies immediately if taken (`暱稱「X」已經被其他人綁定了...`) without writing anything, and stays in `awaiting_nickname` so the next message can retry. If free: fetches `displayName` via `getLineUserProfile` (new, `src/lib/line/client.ts`) and `upsert`s `community_line_bindings` on `line_user_id` with `requested_nickname` + `review_status='pending'` — leaves `nickname` alone (only the admin-approval PATCH ever sets that column, unchanged).
- If already `review_status='pending'`, re-triggering "我要下單" just replies with a "still under review" message instead of asking again. If already `approved`, replies with the 功能二 opening message (see below). An already-approved user CAN re-trigger this to request a nickname change (goes back to `pending`) — this reuses the exact same upsert path.

### 功能二：LINE 圖片下單對話流程

- Opening message on "我要下單" once approved: `已開啟下單功能，請上傳您要的商品圖片（單次最多 10 張），傳完後請回覆「好了」，我就會列出所有收到的商品讓您填寫數量！` (verbatim per spec).
- **Every image message** from an approved+bound user (not gated behind having clicked "我要下單" first — there's no separate "ordering session active" flag; any photo from a bound user is treated as an order photo, matching the "不用做複雜的對話管理系統" instruction) is: downloaded via the new `downloadLineMessageContent` (`GET https://api-data.line.me/v2/bot/message/{id}/content`), uploaded to the private `community-livestream-photos` bucket at `{lineUserId}/{messageId}.jpg`, run through `recognizeProductPhoto` (Anthropic vision, see below), then inserted as one `community_livestream_orders` row (`quantity: 1`, `source: 'line'`, `carousel_sent_at: null`). An unbound/unapproved user sending an image gets a blocking reply instead and nothing is stored.
- **10-per-round cap**: before inserting, counts existing rows for that user with `carousel_sent_at is null`. If already ≥10, the new photo is still downloaded/stored/recognized (nothing is ever discarded), but the reply is the over-cap warning (`這輪已收到 10 張，請先回覆「好了」...`) instead of the normal per-photo ack; it stays queued (`carousel_sent_at` still null) for whatever "好了" comes next. Below 10, replies with a small per-photo ack showing the recognized name/price (or "辨識不出來" if null) and a running count.
- **"好了"/"傳完了"/"完成" (loose substring match, see `DONE_KEYWORDS`)** fetches all rows for that user with `carousel_sent_at is null` (oldest first, capped at 50 = 10×5), batches them into groups of 10 (LINE's Flex carousel hard limit is 12 bubbles; 10 was chosen to match the "one round" size), builds up to 5 such Flex-carousel messages (LINE's reply-call limit is 5 messages), sends them all in **one reply call**, and marks every row actually included as `carousel_sent_at = now()`. If there happen to be more than 50 un-sent rows (customer kept uploading past multiple warnings — an edge case, not expected in normal use), the overflow simply stays queued for the next "好了", same as the 10-per-round overflow above.
- **Carousel bubble**: hero image is a **signed URL with a 7-day expiry** (`CAROUSEL_IMAGE_SIGNED_URL_TTL_SECONDS`), not the short admin-view TTL — LINE's client fetches/caches the image when the user actually views the message, which can be well after send time, so it needs to still be valid then. This is a deliberate trade-off: the bucket itself stays fully private (per spec), but the carousel image URL is a long-lived credential embedded in a message LINE's servers and the customer's device can both see. Documented here as a known/accepted design point, not a gap.
- Footer buttons per bubble: `2件`/`3件`/`4件` are `postback` actions that directly **set** (not add to) `quantity` on that row and reply with a confirmation text (`已將「X」數量更新為 N 件。`) — per spec, the Flex message itself never visually updates (LINE platform limitation), so the confirmation always comes as a separate text reply. `5件以上` is a `postback` that sets `community_line_bot_states.awaiting_quantity_for_order_id` for that user and replies asking them to type a number; the next text message, if a valid positive integer, applies the same quantity-set logic and clears the awaiting state (invalid input replies asking again, state stays set so they can retry).

### 功能三：後台「社群連線訂單」頁籤

- New tab in the existing `lily-backend.html` (submodule), under 社群管理 → 社群連線訂單 — same backend, same deploy, no new site.
- **One table, not two**: `community_livestream_orders` is simultaneously the bot's "待確認佇列" and the final admin-visible order list — a photo becomes a row the moment it's recognized (`quantity` defaulting to 1, `purchase_status='not_bought'`, `payment_status='unpaid'`), and the LINE quantity-buttons/typed-number flow just updates that same row's `quantity` in place. There was never a need for a separate staging table.
- Fields: LINE 名稱, 社群暱稱, 下單商品 (editable text input), 數量 (editable number input), 單價 (editable number input, blank = null/unrecognized), 總價 (`total_price`, a **generated column** — `unit_price * quantity`, or null if `unit_price` is null — never an input, purely computed/read-only in both the DB and the UI), 購買狀態 (未購買/確認中/已購買 dropdown), 匯款狀態 (未付款/確認中/已付款 dropdown), 備註 (editable text input). Every edit is a `PATCH /api/backend/community/livestream-orders/[id]` call, one field at a time (same "onchange autosave" pattern used everywhere else in this admin).
- Status dropdowns reuse the existing `communityStatusSelect`-style visual (a `<select>` with a tone-colored class), but through **new, separate** functions `communityLivestreamStatusSelect`/`communityLivestreamStatusTone` — the existing `communityStatusTone` is hardcoded into `communityStatusSelect`'s `onchange` string (not parameterized), and its red/green mapping is tuned for the *old* system's status values (e.g. `unpaid` → green there); reusing it as-is for this feature's `unpaid`/`paid`/`not_bought`/`bought` values would show backwards colors. The old function/table are completely untouched.
- Mobile-first card list (`.community-livestream-card`, one order per card — a thumbnail + editable fields stacked vertically), not a table with horizontal scroll, per spec.
- Search: a single keyword box matched client-side (JS `.includes()` after fetch) across LINE 名稱/社群暱稱/商品名 on the already-loaded (server status/unrecognized-filtered, capped at 500 rows) result set — no new search RPC. Was a deliberate choice over building a raw `.or()` ilike filter string from free-text input (easy to get the escaping wrong; this table has no dedicated search RPC the way `community_orders`/`community_shipment_requests` do).
- 7 one-click filter buttons (未購買/確認中/已購買/未付款/確認中/已付款/無法辨識價格 — the last one is `unit_price is null`), each independently toggleable (click again to clear), combine via `AND` when more than one is active; state lives in `communityLivestreamFilters` and round-trips through `GET .../livestream-orders?purchaseStatus=&paymentStatus=&unrecognizedOnly=1&q=`.
- Excel export: pure client-side (`XLSX.utils.json_to_sheet` + `XLSX.writeFile`, the same SheetJS CDN script `lily-backend.html` already loads) over whatever's currently loaded/filtered — no new API endpoint needed for this direction.
- Excel import ("手動新增訂單", not a LINE-bot backfill): same client-side `XLSX.read` + header-alias matching (`communityHeaderIndex`, reused as-is) pattern as the existing 記事本 import, landing in `POST /api/backend/community/livestream-orders/import` → `community_livestream_orders` with `source='excel_import'`, `line_user_id: null` (no real LINE identity for a manually-typed row, so no push notification will ever fire for these rows even after 功能四's trigger condition is met — that's expected, not a bug).

### 功能四：訂單確認後的通知

- `PATCH /api/backend/community/livestream-orders/[id]` fires exactly one LINE **push** (`sendLineUserText`, existing function, completely unmodified) the first time `purchase_status` transitions to `'bought'` on a row that has a `line_user_id` (Excel-imported rows never push, per above) — guarded by `confirmed_notified_at` so any later edit (notes, quantity, flipping the status back and forth again) never re-sends it. This is the **only** push in this entire feature; every single other reply anywhere in 功能一/二 goes through `sendLineReply`/`sendLineReplyText`/`sendLineReplyFlex` (new, `src/lib/line/client.ts`), which do not count against the LINE OA's monthly message quota.
- "標記完成/確認" in the task description was interpreted as *purchase* confirmation specifically (`purchase_status → 'bought'`), not payment confirmation — in a livestream-order context, "we actually got you the item" is the moment that matters to the customer, and that's independent of whether payment happened before or after. If this reading turns out to be wrong, this is a one-line condition change (`patch.purchase_status === 'bought'` → whatever the real trigger should be) in that same route.

### New library files (all `server-only`)

- `src/lib/line/webhook-security.ts` — `verifyLineWebhookSignature(rawBody, signatureHeader)` (HMAC-SHA256 with `LINE_CHANNEL_SECRET`, `timingSafeEqual` comparison) + `isLineWebhookConfigured()`.
- `src/lib/line/vision.ts` — `recognizeProductPhoto(buffer, contentType)`, plain `fetch` to `https://api.anthropic.com/v1/messages` (model `claude-sonnet-5`, vision content block), no SDK dependency added (matches this codebase's existing "plain fetch, no provider SDKs" convention for `src/lib/line/client.ts`). Returns `{ productName, price, confidence }` with any/all fields `null` if the model can't determine them — never guesses. Returns `null` entirely only if it couldn't run at all (no API key / network / provider error).

First use of Supabase Storage anywhere in this codebase (everything else uses Cloudinary, which is a **public**-URL service — wrong fit for private customer photos, so this feature uses Supabase Storage instead, not Cloudinary).

- `src/lib/line/client.ts` — extended (not replaced) with `sendLineReply`/`sendLineReplyText`/`sendLineReplyFlex` (reply, never throws — logs+returns `disabled:true` on any failure so a webhook handler always resolves cleanly), `getLineUserProfile`, `downloadLineMessageContent`. ## Community LINE notifications (v1 — manual admin batch send)

- **Not automatic.** An earlier version of this round fired notifications automatically on status change (bought/arrived/marketplace-link-set); that was explicitly reverted. The 3 routes it touched (`order-items/[id]` PATCH, `notebooks` PATCH, `shipment-requests/[id]` PATCH) are back to exactly their pre-notification behavior.
- General batch flow (訂單明細): admin checks order rows (same checkboxes the batch status-update feature uses), picks a type from "LINE 通知類型" — now only **通知付款 / 到貨提醒** (賣貨便可下單 was removed from here, see below) — clicks "LINE 通知". Only the customers behind the checked rows are notified.
- `POST /api/backend/community/line-notifications` — body `{ orderIds, kind }`, `kind` validated against `COMMUNITY_LINE_BATCH_NOTIFICATION_KINDS = ['bought','arrived']` — looks up each order's nickname, dispatches via `src/lib/line/community-notifications.ts::sendCommunityOrderNotifications`, returns per-order results + `successCount`/`failedCount` for the toast.
- **Deduped by recipient**: `sendCommunityOrderNotifications` resolves every selected order to its bound LINE user id first, groups by that id, and sends exactly one LINE message per distinct recipient — a buyer with multiple selected orders gets one message, not one per order. Each order in the group still gets its own `community_line_notifications` row and its own entry in the returned results (same outcome as the one send), so status is still visible per selected order.
- **賣貨便可下單 moved to a dedicated per-出貨申請 action**: each card in the 出貨申請 list gets a "發送賣貨便通知" button, shown whenever that card has a `marketplace_url` and isn't `completed`/`cancelled` — **including after it has already been sent once**; the button is never hidden due to prior send history (only the shipment status itself, same as before). The admin never types a link in here. Click → `POST /api/backend/community/shipment-requests/[id]/notify` (empty body) → `sendCommunityShipmentMarketplaceNotification(shipmentRequestId)` reads nickname/order_ids/marketplace_url **fresh from the DB at send time** (so it always reflects whatever was last saved via the 賣貨便連結 input, single or batch, never a stale client value), builds `{{商品清單}}` from its own `order_ids`, sends, and records with `target_id` = the **shipment request id** (not an order id, since this trigger is scoped to one shipment request which may cover several orders for the same customer). The old "送出 LINE 下單通知" button (a manual completion marker that predated real LINE sending — just a confirm() + status→`completed`) has been **removed**; the status dropdown on each card already covers marking a request completed.
- **發送時間 field (no migration)**: each 出貨申請 card shows an independent "發送時間" field with the most recent 賣貨便可下單 send time for that request, or "尚未發送". Sourced from the existing `community_line_notifications` table — `recordNotification` already `upsert`s on `(kind, target_id)` on every send, so `sent_at` is already "most recent send" with zero schema change; `GET /api/backend/community/shipment-requests` now also reads `sent_at` for `kind='marketplace_ready'` per request id (query wrapped in its own try/catch, so a not-yet-migrated table just shows no time instead of breaking the list). After a send, the frontend reloads both the notification log and the shipment list so this field updates immediately.
  - **Known limitation, not built**: because the table is `unique(kind, target_id)`, each resend overwrites the same row — there is **no full per-send history** (only the latest time is ever retrievable). A fully traceable log of every individual send would need a new append-only table (a migration), which was intentionally **not** created this round per instructions to report before any schema change. Flagged here for a decision next round if the full history is actually needed.
- **賣貨便連結 editing — single and batch, no popup**: the 出貨申請 card's 賣貨便連結 field shows a text input pre-filled with the current `marketplaceUrl` + a 保存 button, for any card not `completed`/`cancelled` (those keep the old read-only "開啟連結" display). Single-row 保存 client-validates HTTPS, then calls `updateCommunityShipmentStatus` (same PATCH endpoint, same pending→accepted auto-transition as before). A "一鍵編輯連結" button (top-right of the 出貨申請 section, enabled once ≥1 card is checked) opens a modal that groups the checked requests **by buyer (nickname)** — one buyer with several requests/notebooks/products gets exactly one link input. **Compressed this round** to two lines per buyer: line 1 is `客人名稱 / LINE 暱稱 / 記事本名稱` only, line 2 is just the link input — the previous 商品明細 list and "包含記事本：" line were removed so many more buyers fit on screen without scrolling; `communityShipmentBuyerGroups()` still collects `items`/notebook names internally (harmless, just unused by this modal's markup now). One 保存 fires all the underlying PATCH calls together (`Promise.all`, admin doesn't wait row by row), then the card list reloads so every affected card's inline input shows the new value immediately. Batch save reuses the same single-request PATCH endpoint and pending→accepted transition — no new API, no migration. `editCommunityShipmentMarketplace`/`window.prompt()` remain gone; there is no prompt/popup/new-window anywhere in `lily-backend.html`.
- Recipient resolution (both paths): `community_line_bindings` where `review_status = 'approved'`, matched by nickname.
- Send: `sendLineUserText` in `src/lib/line/client.ts` (same pattern as the existing `sendLineAdminText`/`sendLineUserFlex`), using `LINE_CHANNEL_ACCESS_TOKEN` (confirmed configured on Vercel Preview).
