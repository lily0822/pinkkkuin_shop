## LINE 圖片下單 + 社群連線訂單 (new feature, this round — not yet usable end-to-end)

A brand-new, fully independent feature: customers order by sending photos of products directly to the LINE Official Account chat, no website involved. Does **not** touch `community_orders`/`community_order_items`/the existing 記事本 system in any way, and does **not** change the existing admin-approval binding review page/API (`社群名單` tab, `/api/backend/community/members`) — this round only adds a *customer-facing, self-service* path that writes into the same `community_line_bindings` table using columns that page already reads.

**Entirely reply-based, zero push, by deliberate design.** The feature originally had one push (訂單已確認, on 購買狀態→已購買) — it was removed in a later round because the user decided it wasn't needed; every remaining message anywhere in this feature (binding, image ordering, quantity updates, self-service remittance) already only ever used `sendLineReply`/`sendLineReplyText`/`sendLineReplyFlex`, which don't count against the LINE OA's monthly message quota. Backend edits (including marking a row 已購買) are now pure database updates with no customer-facing side effect at all — see 功能四 below for the removal detail.

### Configurable trigger keywords (cuts across 功能一/二/五/六)

Five trigger-keyword lists that used to be (or would otherwise have been) hardcoded arrays in `src/lib/line/livestream-orders.ts` are backend-editable, **no new migration**:

- `src/lib/line/livestream-keywords.ts` — `DEFAULT_LIVESTREAM_KEYWORDS` holds the default list for all 5 groups (`order`/`done`/`remittance`/`cancel`/`quantity_confirm` — the last one added in a later round, default `數量正確`), `getLivestreamKeywords()` reads the admin-saved override from `schedule_settings` (`type='community-livestream-keywords'`, JSON in `image` — same generic-KV pattern as `livestream-bank-info.ts`/`community-notification-templates.ts`, no new table) and **falls back to the defaults on any read failure or if nothing's been saved yet** — so a backend that's never touched this settings screen behaves exactly as before. `handleTextMessage` calls this once per incoming text message (a single extra query, not one per keyword-group check) rather than reading module-level constants. Adding `quantity_confirm` also prompted a small refactor: `getLivestreamKeywords`/`saveLivestreamKeywords` now loop over `LIVESTREAM_KEYWORD_GROUPS` (via a shared `sanitizeAllGroups` helper) instead of naming each of the 4 groups by hand — so a future 6th group only needs to be added to the `LivestreamKeywordGroup` type, `LIVESTREAM_KEYWORD_GROUPS`, `LIVESTREAM_KEYWORD_GROUP_LABELS`, and `DEFAULT_LIVESTREAM_KEYWORDS`, not touched in 3+ separate places.
- `GET`/`POST /api/backend/community/livestream-keywords` — same auth-guard shape as the other backend routes in this feature. `POST` sanitizes each group (non-empty strings, capped length/count) and, before saving, runs `findDuplicateKeywords()` — an **exact-match** (case-insensitive) check for the same keyword appearing in more than one group. If any are found and the request didn't pass `force: true`, it responds `{ ok:false, needsConfirm:true, duplicates:[...] }` instead of erroring outright — this is a soft warning, not a hard block, per instructions ("跳個提示讓管理員自己決定要不要繼續存"). The route also loops over `LIVESTREAM_KEYWORD_GROUPS` to build the incoming payload, so it didn't need touching when `quantity_confirm` was added.
- Backend UI: a "關鍵字設定" toolbar button (社群連線訂單 section, alongside 收款帳號設定) opens a modal with one textarea per group (下單/完成/匯款/取消/數量確認), one keyword per line or comma-separated — the frontend's own load/save/duplicate-check logic already iterated `Object.keys(COMMUNITY_LIVESTREAM_KEYWORD_GROUP_LABELS)` generically, so adding the 5th group only needed one new textarea + one new map entry, not new JS logic. On save, if the API responds `needsConfirm`, the frontend shows a `confirm()` listing which keyword collides across which groups (in Chinese group names) and, if confirmed, resubmits with `force:true` — no separate "are you sure" UI component, just the browser's own `confirm()`.
- The `cancel` group (功能六's trigger keywords) was included in the same round the other 3 original groups were made configurable, even though the request only explicitly asked about the other three — the user asked "順便問一下...建議一起做" and confirmed doing all four then rather than opening a separate round later for it. `quantity_confirm` (功能二's "數量正確" lock trigger, see below) was added in a later round as its own new feature, not part of that original batch.
- Not yet manually tested (needs the pending migrations + a bound test LINE account, same blocker as everything else in this feature) — see the updated manual test list below.

### 功能一：LINE 帳號綁定（自助式）

- `src/lib/line/livestream-orders.ts::handleTextMessage` — on any text message from a user with no binding row (or `review_status` other than `pending`/`approved`), matching one of the `order` keyword group (default `我要下單`/`下單`/`開始下單`/`開通`/`綁定`/`加入社群`/`註冊`, loose substring match, **backend-configurable this round** — see "Configurable trigger keywords" above) sets `community_line_bot_states.awaiting_nickname = true` and replies asking for the nickname. The very next text message from that user (regardless of content) is read as the nickname, not matched against any keyword.
- Nickname submission: checks for a collision against **already-approved** bindings only (`ilike` on `nickname`, excluding this same `line_user_id` — the exact same rule `src/app/api/backend/community/members/route.ts::validateNickname` already uses for the admin-approval flow), replies immediately if taken (`暱稱「X」已經被其他人綁定了...`) without writing anything, and stays in `awaiting_nickname` so the next message can retry. If free: fetches `displayName` via `getLineUserProfile` (new, `src/lib/line/client.ts`) and `upsert`s `community_line_bindings` on `line_user_id` with `requested_nickname` + `review_status='pending'` — leaves `nickname` alone (only the admin-approval PATCH ever sets that column, unchanged).
- If already `review_status='pending'`, re-triggering "我要下單" just replies with a "still under review" message instead of asking again. If already `approved`, replies with the 功能二 opening message (see below). An already-approved user CAN re-trigger this to request a nickname change (goes back to `pending`) — this reuses the exact same upsert path.

### 功能二：LINE 圖片下單對話流程

- Opening message on "我要下單" once approved: `已開啟下單功能，請上傳您要的商品圖片（單次最多 10 張），傳完後請回覆「好了」，我就會列出所有收到的商品讓您填寫數量！` (verbatim per spec).
- **Every image message** from an approved+bound user (not gated behind having clicked "我要下單" first — there's no separate "ordering session active" flag; any photo from a bound user is treated as an order photo, matching the "不用做複雜的對話管理系統" instruction) is: downloaded via `downloadLineMessageContent` (`GET https://api-data.line.me/v2/bot/message/{id}/content`), uploaded to the private `community-livestream-photos` bucket at `{lineUserId}/{messageId}.jpg`, run through `recognizeProductPhoto` (Anthropic vision, see below), then inserted as one `community_livestream_orders` row (`quantity: 1`, `source: 'line'`, `carousel_sent_at: null`). An unbound/unapproved user sending an image gets a blocking reply instead and nothing is stored.
- **Silent upload, by design (changed this round)**: uploading photos no longer gets a per-photo reply at all — the "已收到第 N 張圖片..." ack was removed because the user found it too chatty. The customer hears nothing back until they reply "好了". The **one exception** is still the 10-per-round warning (see below) — without it a customer would have no idea a later photo wasn't included in the current round.
- **Auto-generated product name when recognition fails (changed this round)**: `product_name` is **never** written as `null` and the bot never shows "未辨識商品" anywhere. When `recognizeProductPhoto` can't determine a name, `generateFallbackProductName` builds `{LINE顯示名稱}-商品{N}` — `N` is simply "how many `community_livestream_orders` rows this `line_user_id` already has" (counted fresh from the DB each time, not a separate counter column), so it naturally keeps incrementing across rounds/batches without ever resetting, and every downstream reader of `product_name` (Carousel bubbles, the quantity-confirmation reply, the backend list) picks it up automatically with no separate change needed. Note: like the pre-existing `countPendingPhotos`/10-cap check, this count-then-insert has the same theoretical race if a customer's photos are processed concurrently (multiple images in one LINE webhook payload) — not a new regression, just the same tolerance level the rest of this file already has.
- **10-per-round cap**: before inserting, counts existing rows for that user with `carousel_sent_at is null`. If already ≥10, the new photo is still downloaded/stored/recognized (nothing is ever discarded) and the over-cap warning reply (`這輪已收到 10 張，請先回覆「好了」...`) is sent; it stays queued (`carousel_sent_at` still null) for whatever "好了" comes next. Below 10: no reply at all now (see "silent upload" above).
- **"好了"/"傳完了"/"完成" (loose substring match against the configurable `done` keyword group, see "Configurable trigger keywords" above)** fetches all rows for that user with `carousel_sent_at is null` (oldest first), batches them into groups of 10 (kept at the same size as before — see the layout change below for why 12 no longer strictly applies), and sends them in **one reply call** that starts with a leading text message — `已登錄您的商品，請確認以下數量：` — followed by the Flex message batches. LINE's reply-call hard limit is 5 messages total, and the leading text uses one of those slots, so capacity is 4 batches (40 photos) per "好了" — the fetch `.limit(...)` matches. Every row actually included gets `carousel_sent_at = now()`; anything beyond the 40-photo cap (an edge case, not expected in normal use) simply stays queued for the next "好了", same as the 10-per-round overflow above.
- **Quantity-confirmation layout: single vertical Flex bubble, not a Carousel (changed this round)**: each batch of up to 10 items is now rendered as **one Flex bubble whose body stacks every item vertically** (`buildOrderItemBlock` builds one item's thumbnail+name+price/qty text+quantity-button row; `buildOrderListBubble` joins them with `separator`s into a single bubble), instead of the previous 10-bubble horizontal Carousel. The customer scrolls down through one chat bubble instead of swiping sideways through cards. Each item's quantity buttons are unchanged — still independent `postback`s carrying their own `order_id`, nothing shared/merged between items. Batch size (10) and the reply-call capacity (4 batches / 40 photos) are **unchanged** — the user asked to keep it "跟現在差不多，例如 10-20 筆", and 10 was already in that range, so this was a pure layout change with no batching-size change. `CAROUSEL_IMAGE_SIGNED_URL_TTL_SECONDS` (7-day signed URL, same trade-off rationale as before) is now used by `buildOrderItemBlock`'s per-item thumbnail instead of a per-bubble `hero` image — same signed-URL mechanism either way. **功能六's cancel-order Carousel (`buildCancelBubble`) is untouched** — the request only asked to change the quantity-confirmation screen, not the cancel flow, so that one still uses horizontal Carousel cards exactly as before.
- **No "價格未辨識" text either**: when `unit_price` is null, the item block's detail line drops the price entirely and just shows `目前數量：N` — no price-related wording of any kind, consistent with the product-name auto-generation above. The block just looks like a normal, slightly-less-detailed product entry, not a "recognition failed" notice.
- Per-item quantity buttons: `2件`/`3件`/`4件` are `postback` actions that directly **set** (not add to) `quantity` on that row and reply with a confirmation text (`已將「X」數量更新為 N 件。`) — per spec, the Flex message itself never visually updates (LINE platform limitation), so the confirmation always comes as a separate text reply. `5件以上` is a `postback` that sets `community_line_bot_states.awaiting_quantity_for_order_id` for that user and replies asking them to type a number; the next text message, if a valid positive integer, applies the same quantity-set logic and clears the awaiting state (invalid input replies asking again, state stays set so they can retry). The confirmation text's old `product_name ? ... : "這項商品"` fallback was removed in an earlier round — `product_name` is guaranteed non-null now, so the reply always shows the real (or auto-generated) name.
- **"數量正確" locks quantity adjustment for that batch (new this round)**: the "好了" opening text now reads `已登錄您的商品，請確認以下數量，如果都沒問題請回覆「數量正確」：`. Replying with the `quantity_confirm` keyword group (default `數量正確`, backend-configurable — see "Configurable trigger keywords" above) triggers `handleQuantityConfirmTrigger`, which sets `quantity_locked_at = now()` on every one of that customer's rows where `carousel_sent_at is not null` (already listed in some "好了" batch) **and** `quantity_locked_at is null` (not already locked) — replies `目前沒有待確認的商品數量喔。` if there's nothing to lock, otherwise `以上已經記錄囉！`. Because the lock only ever targets rows that have been shown and aren't locked yet, a **later** round of photos (fresh rows, `carousel_sent_at` still null at lock time) is never affected by an earlier lock — no cross-round leakage. LINE can't make an already-sent button visually unclickable, so this is a **functional** lock, not a visual one: `applyQuantityUpdate` (the single function behind both the `2/3/4件` postbacks and the `5件以上` typed-number flow) now checks `quantity_locked_at` before writing anything — if set, it replies `此訂單數量已確認，如需修改請聯繫客服。` and the database `quantity` is left untouched; the button remains tappable, it just silently no-ops at the server.

### 功能三：後台「社群連線訂單」頁籤

- New tab in the existing `lily-backend.html` (submodule), under 社群管理 → 社群連線訂單 — same backend, same deploy, no new site.
- **One table, not two**: `community_livestream_orders` is simultaneously the bot's "待確認佇列" and the final admin-visible order list — a photo becomes a row the moment it's recognized (`quantity` defaulting to 1, `purchase_status='not_bought'`, `payment_status='unpaid'`), and the LINE quantity-buttons/typed-number flow just updates that same row's `quantity` in place. There was never a need for a separate staging table.

### 功能四：訂單確認後的通知 — **removed** (this round)

- Originally: `PATCH /api/backend/community/livestream-orders/[id]` fired exactly one LINE **push** (`sendLineUserText`) the first time `purchase_status` transitioned to `'bought'` on a row with a `line_user_id`, guarded by `confirmed_notified_at` so later edits never re-sent it. **This has been removed** — the user decided the notification wasn't needed, since it was the only action in this entire feature that counted against the LINE OA's monthly message quota.
- Current behavior: the `PATCH` route now does a plain database update and nothing else — no `before`-row lookup, no push, no `notified` field in the response. Marking a row 已購買 (individually or via 功能三's batch tool) is silent from the customer's side.
- `confirmed_notified_at` (the column that used to guard against re-sending) is **left in the table as-is** — not read, not written, no migration to drop it. Removing an unused column wasn't worth a schema change for this; it's simply dead weight in `community_livestream_orders` now.
- This means the feature has **zero push messages anywhere** — see the note at the top of this section.

### 功能五：自助匯款申報 (new this round)

Brand-new LINE conversation flow, same trigger/reply pattern as "我要下單" (功能一/二). Only ever touches `community_livestream_orders.payment_status` and the new `community_livestream_remittances` table — does **not** touch `community_orders`/`community_remittance_submissions` (that older table stores the *customer's own* bank account the money came from, for the separate 記事本 system; this feature stores "which of *this* system's orders a report is meant to reconcile", a different concern entirely).

- Trigger: the `remittance` keyword group (default `我要匯款`/`匯款申報`/`回報匯款`/`匯款`, loose substring match, backend-configurable — see "Configurable trigger keywords" above), gated behind the same approved-binding check as image ordering (`isApprovedBinding`) — an unbound/pending customer gets a blocking reply, nothing else happens.
- On trigger, `handleRemittanceTrigger` queries that user's own `community_livestream_orders` where `payment_status = 'unpaid'`:
  - If **any** matching row has `unit_price is null` (unrecognized), the whole batch is blocked — replies `您有 N 項商品尚未確認金額，請等候客服確認金額後才能匯款，確認後可以再次輸入「我要匯款」。` and creates nothing (no state change, no DB row).
  - Otherwise, sums `total_price` across all of them, lists each as `商品名稱 ×數量　NT$小計`, appends the 收款帳號設定 text (see 功能三 above) if any is saved, and asks the customer to reply with their remittance account's last 5 digits.
- **State snapshot, not live recompute**: at trigger time, `community_line_bot_states.awaiting_remittance_last5` is set `true` and the exact `order_ids` + computed `amount` are written into that same table's new `remittance_order_ids`/`remittance_amount` columns. When the customer's last-5-digits reply comes in (possibly minutes later), the code reads that snapshot back rather than re-querying/re-summing — so an admin edit to a price/quantity in between can't silently change what gets recorded as "what the customer was told and agreed to pay."
- `handleRemittanceLast5Submission` validates the reply as exactly 5 digits (`parseAccountLast5`, `/^\d{5}$/`) — an invalid reply gets `請輸入正確的匯款帳號後 5 碼（純數字 5 碼）...` and the awaiting state is **not** cleared, so the customer can just retry (same pattern as the existing quantity-input flow). On a valid reply: inserts one row into `community_livestream_remittances` (`line_user_id`, `nickname`, `order_ids`, `account_last5`, the snapshotted `amount`, `submitted_at`), updates all of those `order_ids`' `payment_status` to `confirming`, clears the bot state, and replies `已收到您的匯款回報，我們將盡快為您核對，感謝您！`. A DB failure on the insert also leaves the state intact so the customer isn't forced to re-trigger the whole flow just to retry the same 5 digits.
- Admin side: the reported last-5 + declared amount show on the order's card once `payment_status='confirming'` (功能三 above); after the admin reconciles against the bank statement, they use 功能三's batch tool to flip the reconciled cards' 匯款狀態 to 已付款 in one action.
- Entirely reply-based like 功能一/二 — no push (功能四's push was removed entirely in a later round, see above; this flow was never affected by it either way since it only ever touched `payment_status`, not `purchase_status`).

### 功能六：自助取消訂單 (new this round)

Brand-new LINE conversation flow, same trigger/reply pattern as "我要下單"/"我要匯款". Only ever touches `community_livestream_orders` — a customer can only cancel their own **not-yet-purchased** items, and cancelling means the row is gone (hard delete, no cancellation log/audit trail — explicitly deferred, not built this round).

- Trigger: the `cancel` keyword group (default `取消訂單`/`我要取消`/`取消`, loose substring match, backend-configurable — see "Configurable trigger keywords" above), gated behind the same approved-binding check as the other flows.
- `handleCancelTrigger` queries that user's own `community_livestream_orders` where `purchase_status = 'not_bought'` (oldest first, capped at 50 like the other list-building flows):
  - None found → replies `目前沒有可以取消的商品喔（已購買的商品無法取消）。` and stops.
  - Otherwise builds a Flex Carousel (same batching as 功能二's carousel — groups of 10, up to 4 batches since one slot is used by the leading text message, so up to `MAX_REPLY_MESSAGES - 1` batches) of the cancellable rows only (thumbnail + product name + quantity, no price), each bubble with one red "取消這項" postback button (`action=cancel_order&order_id=...`). A leading text message is prepended: if the customer also has any `bought` rows, it says `您已購買的 N 項商品不會列在這裡，恕無法取消。以下是可以取消的商品：`; otherwise just `以下是您目前可以取消的商品：`.
- Tapping "取消這項" → `handlePostback`'s new `cancel_order` branch → `handleCancelOrder`: re-reads that row scoped by **both** `id` and `line_user_id` (so a customer can't cancel someone else's order id even by guessing/replaying an old postback), re-checks `purchase_status === 'not_bought'` (defends against a race where the admin bought it in the meantime — replies `這項商品已經購買，無法取消。` if so), then calls the same `deleteLivestreamOrder` the backend's delete button uses, and replies `已為您取消「商品名稱」，感謝您的訂購！`.
- No push anywhere in this flow — same reply-only design as the rest of the feature.

## Community LINE notifications (v1 — manual admin batch send)

- **Not automatic.** An earlier version of this round fired notifications automatically on status change (bought/arrived/marketplace-link-set); that was explicitly reverted. The 3 routes it touched (`order-items/[id]` PATCH, `notebooks` PATCH, `shipment-requests/[id]` PATCH) are back to exactly their pre-notification behavior.
- General batch flow (訂單明細): admin checks order rows (same checkboxes the batch status-update feature uses), picks a type from "LINE 通知類型" — now only **通知付款 / 到貨提醒** (賣貨便可下單 was removed from here, see below) — clicks "LINE 通知". Only the customers behind the checked rows are notified.
- `POST /api/backend/community/line-notifications` — body `{ orderIds, kind }`, `kind` validated against `COMMUNITY_LINE_BATCH_NOTIFICATION_KINDS = ['bought','arrived']` — looks up each order's nickname, dispatches via `src/lib/line/community-notifications.ts::sendCommunityOrderNotifications`, returns per-order results + `successCount`/`failedCount` for the toast.
