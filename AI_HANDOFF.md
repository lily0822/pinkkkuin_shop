## Production incident: tesseract.js crashed every image upload (this round)

**What happened**: the user reported Vercel **Production** logs showing `recognizePriceFromPhoto` (the free OCR fallback added in prior rounds) crashing the entire Node process on every image message: `Error: Cannot find module '/ROOT/node_modules/tesseract.js/src/worker-script/node/index.js'`, `Node.js process exited with exit status: 129`. This wasn't a graceful OCR failure — it took down all of `handleImageMessage`, so the customer's photo never got written to the DB at all, on **every single image message**, in Production.

- **This was the first indication Production is live and receiving real traffic for this feature.** Nothing in this file's prior rounds ever recorded deploying this feature (or anything) to Production — seeing this crash in a real Production log, and then confirming via `vercel ls --prod`/`vercel alias ls` that Production deploys to `pinkkkuin-shop.vercel.app` happen independently and frequently (see baseline note above), was the first evidence of that. How/when the LINE webhook got pointed at Production, the 6 migrations got applied there, `ANTHROPIC_API_KEY` etc. got configured — none of that is known or documented anywhere in this file. Worth asking the user directly next time Production state matters, rather than assuming the "Production go-live checklist" section further below (written when this feature only existed on Staging) still reflects reality.
- **Step 1 — immediate hotfix (deployed to Production within minutes of the report)**: removed the `recognizePriceFromPhoto` call from `handleImageMessage` entirely (not wrapped in try/catch — the crash kills the whole process before our own code's try/catch would ever run, so wrapping it would not have helped). Restores exactly the pre-OCR-feature behavior: `unit_price` stays `null` when Anthropic doesn't find one, same as before this OCR feature ever existed — not a regression, a return to the last known-good state. Verified locally (`tsc`/`eslint`/`npm run build`), then deployed with `vercel deploy --prod --yes` **and explicitly re-aliased to `pinkkkuin-shop.vercel.app`** (the first `--prod` deploy only auto-aliases to the generic `pinkkkuin-shop-lilys-projects-2a8e834c.vercel.app` URL — the actual custom domain alias has to be set separately with `vercel alias set`, or the fix silently doesn't reach real traffic). Confirmed via `curl -X POST https://pinkkkuin-shop.vercel.app/api/line/webhook` returning `401` (not `500`) that Production was no longer crashing.
- **Step 2 — root-caused and fixed properly, verified on a real Vercel Staging deployment (not just local checks) before being trusted**:
  - `outputFileTracingIncludes` (the standard, commonly-cited fix for "file missing after Vercel deploy") was tried first and **did not work** — confirmed by inspecting the actual `.next/server/app/api/line/webhook/route.js.nft.json` trace file locally (it *did* list `worker-script/node/index.js` and every dependency), yet the identical crash still happened on a real Staging deploy with that fix in place. This ruled out "file not included in the deployment" as the actual cause.
  - Real root cause (confirmed via [naptha/tesseract.js#868](https://github.com/naptha/tesseract.js/issues/868), a well-documented Next.js/Vercel-specific issue): tesseract.js spawns its OCR worker via `new Worker(path.join(__dirname, ...))` (`src/worker/node/spawnWorker.js`). Turbopack rewrites `__dirname` for bundled modules so it no longer matches where the file actually lives after deployment — the worker thread's own independent module resolution then looks in the wrong place, regardless of whether the right file bytes were included somewhere in the deployment.
  - **The actual fix, matching the two independently-reported working fixes on that GitHub issue**: (1) added `"tesseract.js"` and `"tesseract.js-core"` to `serverExternalPackages` in `next.config.ts` (alongside `"sharp"`, same mechanism as the earlier sharp fix) — this stops Turbopack from touching tesseract.js's own source files at all, so its real on-disk `__dirname` stays correct; (2) passed an explicit `workerPath: "./node_modules/tesseract.js/src/worker-script/node/index.js"` option to `createWorker()` in `price-ocr.ts`, instead of relying on tesseract.js's own computed default — this is resolved relative to the function's working directory at runtime, not a bundler-mangled `__dirname`. `outputFileTracingIncludes` was kept as well (still needed to get the actual `.wasm` core files included in the deployment at all — just not sufficient by itself).
  - **Verified against a real Vercel Staging deployment, not just local tooling** (the explicit lesson from this incident — local `tsc`/`eslint`/`npm run build`/direct `node` runs had all passed throughout, including on the version that crashed in Production): added a temporary diagnostic route (`/api/line/debug-ocr-test`, gated behind the existing backend admin session auth, since the normal path to this code — a real bound LINE test account sending a photo — is blocked by the same long-standing pending-migrations issue that has blocked all end-to-end testing of this entire feature). Logged into the Staging backend via `curl` to get a session cookie, then POSTed each of the 4 real reference photos (`scratch/price-ocr-samples/`) directly to that route against the **actual deployed Staging function**. Result: `280`/`270`/`280`/`null` — exactly matching the expected local results from the prior round, no crash. Cross-checked with `vercel logs` across all test calls — zero `error`-level entries, no "Cannot find module", no exit-129 signatures. Deleted the diagnostic route immediately afterward (its job was done, and it's not something that should linger even behind auth).
- **Current state**: the real fix (commit `32f8a08`) is deployed and verified on **Staging only**. `recognizePriceFromPhoto`'s call site in `handleImageMessage` is back in place in the `official-next` source. **Production still has the Step 1 hotfix (OCR fallback removed entirely)** — the real fix has deliberately not been promoted to Production yet, since that wasn't asked for in this round (scoped explicitly to "restore Production immediately, fix properly on Staging, no rush on re-promoting"). Promoting the real fix to Production is a decision for the user to make explicitly, the same way the emergency hotfix itself required an explicit "deploy immediately" instruction before any Production action was taken this round.

## LINE 圖片下單 + 社群連線訂單 (new feature, this round — not yet usable end-to-end)

A brand-new, fully independent feature: customers order by sending photos of products directly to the LINE Official Account chat, no website involved. Does **not** touch `community_orders`/`community_order_items`/the existing 記事本 system in any way, and does **not** touch the existing admin-approval binding review page/API (`社群名單` tab, `/api/backend/community/members`) at all. The feature originally wrote into `community_line_bindings` for its own customer-facing nickname-approval flow, but that whole mechanism (暱稱綁定/審核) was **removed** in a later round — see 功能一 below — so this feature no longer reads or writes `community_line_bindings` in any way; nickname is now just the customer's live LINE display name.

**Entirely reply-based, zero push, by deliberate design.** The feature originally had one push (訂單已確認, on 購買狀態→已購買) — it was removed in a later round because the user decided it wasn't needed; every remaining message anywhere in this feature (image upload, self-service remittance, self-service cancel) already only ever used `sendLineReply`/`sendLineReplyText`/`sendLineReplyFlex`, which don't count against the LINE OA's monthly message quota. Backend edits (including marking a row 已購買) are now pure database updates with no customer-facing side effect at all — see 功能四 below for the removal detail.

### Configurable trigger keywords (cuts across 功能一/五/六)

Three trigger-keyword lists that used to be (or would otherwise have been) hardcoded arrays in `src/lib/line/livestream-orders.ts` are backend-editable, **no new migration**:

- `src/lib/line/livestream-keywords.ts` — `DEFAULT_LIVESTREAM_KEYWORDS` holds the default list for all 3 groups (`order`/`remittance`/`cancel`), `getLivestreamKeywords()` reads the admin-saved override from `schedule_settings` (`type='community-livestream-keywords'`, JSON in `image` — same generic-KV pattern as `livestream-bank-info.ts`/`community-notification-templates.ts`, no new table) and **falls back to the defaults on any read failure or if nothing's been saved yet** — so a backend that's never touched this settings screen behaves exactly as before. `handleTextMessage` calls this once per incoming text message (a single extra query, not one per keyword-group check) rather than reading module-level constants. `getLivestreamKeywords`/`saveLivestreamKeywords` loop over `LIVESTREAM_KEYWORD_GROUPS` (via a shared `sanitizeAllGroups` helper) instead of naming each group by hand — so a further new group only needs to be added to the `LivestreamKeywordGroup` type, `LIVESTREAM_KEYWORD_GROUPS`, `LIVESTREAM_KEYWORD_GROUP_LABELS`, and `DEFAULT_LIVESTREAM_KEYWORDS`.
- `GET`/`POST /api/backend/community/livestream-keywords` — same auth-guard shape as the other backend routes in this feature. `POST` sanitizes each group (non-empty strings, capped length/count) and, before saving, runs `findDuplicateKeywords()` — an **exact-match** (case-insensitive) check for the same keyword appearing in more than one group. If any are found and the request didn't pass `force: true`, it responds `{ ok:false, needsConfirm:true, duplicates:[...] }` instead of erroring outright — this is a soft warning, not a hard block, per instructions ("跳個提示讓管理員自己決定要不要繼續存"). The route loops over `LIVESTREAM_KEYWORD_GROUPS` to build the incoming payload, so it never needed touching across any of these group additions/removals.
- Backend UI: a "關鍵字設定" toolbar button (社群連線訂單 section, alongside 收款帳號設定) opens a modal with one textarea per group (下單/匯款/取消), one keyword per line or comma-separated — the frontend's own load/save/duplicate-check logic already iterated `Object.keys(COMMUNITY_LIVESTREAM_KEYWORD_GROUP_LABELS)` generically, so adding/removing a group only ever needed a textarea + a map entry, no new JS logic. On save, if the API responds `needsConfirm`, the frontend shows a `confirm()` listing which keyword collides across which groups (in Chinese group names) and, if confirmed, resubmits with `force:true` — no separate "are you sure" UI component, just the browser's own `confirm()`.
- The `cancel` group (功能六's trigger keywords) was included in the same round the other 3 original groups were made configurable, even though the request only explicitly asked about the other three — the user asked "順便問一下...建議一起做" and confirmed doing all four then rather than opening a separate round later for it.
- **`edit_nickname` group removed in the previous round** (the "修改暱稱" feature it backed was deleted along with 功能一's binding/review mechanism). **`done`/`quantity_confirm` removed this round**: the "好了" quantity-confirmation screen and "數量正確" lock mechanism they triggered were both deleted entirely (see 功能二 below) — these two groups and their backend-settings textareas were deleted rather than left as dead UI. Keyword groups have gone from 6 (at their peak) → 5 (nickname round) → **3** (this round): `order`/`remittance`/`cancel`.
- Not yet manually tested (needs the pending migrations, same blocker as everything else in this feature) — see the updated manual test list below.

### Configurable reply templates — 10 customer-facing messages (10 removed this round)

The main-flow reply texts a customer actually sees (下單 welcome, cancel, remittance — **not** the rare internal error/edge-case strings like "圖片下載失敗"/"查詢訂單失敗", which stay hardcoded on purpose) are backend-editable, **no new migration**, same `schedule_settings` generic-KV pattern as everything else in this feature:

- `src/lib/line/livestream-reply-templates.ts` — `DEFAULT_LIVESTREAM_REPLY_TEMPLATES` holds all 10 keys' default text, byte-for-byte identical to what's actually sent, so a backend that's never touched the settings screen behaves exactly as before. `getLivestreamReplyTemplates()` reads the admin override from `schedule_settings` (`type='community-livestream-reply-templates'`, JSON in `image`) and falls back to the defaults on any read failure or missing/blank per-key value (mirrors `livestream-keywords.ts`'s `sanitizeAllGroups` — an admin can't save an empty template, only overwrite or fall back). `renderLivestreamReplyTemplate(template, vars)` does simple `{{var}}` → value substitution, same placeholder syntax as `community-notification-templates.ts`'s `{{商品清單}}`.

Any admin customization previously saved under a now-removed key in the `schedule_settings` JSON blob is simply ignored (`sanitizeTemplates` only iterates the current `LIVESTREAM_REPLY_TEMPLATE_KEYS`) — harmless leftover data, no migration needed since this is a JSON blob not a schema.

- Backend UI: a "訊息文案設定" toolbar button (社群連線訂單 section, next to 關鍵字設定) opens a settings-list modal (10 rows under 3 category headers now — 數量/價格有誤回報/客人自助刪除 groups and all their rows were removed this round — each with a truncated preview + "編輯訊息" button) that reuses the exact same `.community-line-template-*` CSS classes the pre-existing LINE 通知文案設定 modal uses. ### ⚠️ Rich Menu — do not publish to all friends yet

This is a **real** LINE Official Account with **1,546 existing friends**. The new "我要下單" Rich Menu must **not** be set as the account's default/全體 menu until testing is done — every one of those friends would immediately see and be able to trigger the new ordering flow.

### 功能二：LINE 圖片下單對話流程

- Opening message on "我要下單": `已開啟下單功能，請直接上傳您要的商品圖片即可，不需要再輸入其他文字！提醒您：若超過 10 分鐘沒有上傳新照片，請重新輸入「我要下單」繼續使用。`（backend-editable via `order_welcome` — see "Configurable reply templates" above；10 分鐘提醒句是**這輪新加的**，管理員自己改掉這句文字也完全沒問題）— 不需要任何綁定/審核（見功能一），任何 LINE 使用者都能立刻觸發。
- **Every image message** from any LINE user is: downloaded via `downloadLineMessageContent` (`GET https://api-data.line.me/v2/bot/message/{id}/content`), uploaded to the private `community-livestream-photos` bucket at `{lineUserId}/{messageId}.jpg`, run through `recognizeProductPhoto`（Anthropic vision）+ 免費 OCR 備援（見下方，完全沒改動），然後存成一筆 `community_livestream_orders`（`quantity: 1`、`source: 'line'`、`nickname`/`line_display_name` 來自 `getLineDisplayName`，見功能一）——**全程零回覆，沒有任何例外**（見下方「客人端數量/價格互動整組移除」）。
- **Free white-box OCR price fallback** — `src/lib/line/price-ocr.ts::recognizePriceFromPhoto(buffer)`, called from `handleImageMessage` only when `recognizeProductPhoto`'s (Anthropic's) `price` came back `null` (currently: always, since `ANTHROPIC_API_KEY` still isn't set anywhere — see "Not usable yet" above). Zero API cost, two new deps (`sharp` for pixel work, `tesseract.js` for OCR): (1) downscales the photo, scans pixels for high-purity-white (`R/G/B` all ≥225 and within 20 of each other — deliberately stricter than "looks white to the eye" to avoid matching overexposed backgrounds), flood-fills to find **every** connected white region above a 1%-of-image-area minimum (not just the single largest one — see the multi-box bullet below for why); (2) crops **each** candidate region independently (with ~8% padding) from the *original*-resolution image, upscales if small, and OCRs it with a shared `tesseract.js` worker; (3) reads the OCR result **line by line** (not as one text blob) and keeps a line as a price candidate only if, after trimming and stripping commas, it's purely digits. Exactly one numeric candidate across all boxes/lines → used as `unit_price`; zero or more than one (not found / genuinely ambiguous) → `null`, same "don't guess" contract as the Anthropic path, and it never overwrites a price Anthropic already found. The `tesseract.js` worker is created once and kept alive for the life of the warm serverless instance (`cachePath: '/tmp'`, no `.terminate()` call, no character whitelist — see below for why) rather than spun up per photo, to avoid repeatedly paying its WASM-init + language-data-download cost; when a photo has multiple white-box candidates, those are OCR'd **sequentially** against that one shared worker (not `Promise.all`), since a single `tesseract.js` worker can't run two `recognize()` calls concurrently.
- **Handles multiple/touching white boxes, not just the single largest one**: the original version only looked at the largest connected white region and picked the longest digit-run out of its whole OCR text blob. That broke when a photo had a second white-backed sticker near the price (e.g. a Chinese description like "是一個盤子") close enough that flood-fill merged both into **one** connected white region — the whole-blob text search then had digits and Chinese text mixed together with no clean way to separate them. Fixed by (a) collecting **all** sufficiently-large white regions instead of just the largest, so genuinely separate stickers are each OCR'd on their own, and (b) dropping `tessedit_char_whitelist` entirely and instead reading `data.blocks → paragraphs → lines` (tesseract.js's structured per-line output — note this must be explicitly requested via `recognize(image, {}, { blocks: true })`, since `blocks` is `false` in tesseract.js's own default output options) and keeping only lines that are purely numeric after trimming — a Chinese-text line now reads as itself (not force-mapped into digit guesses) and gets correctly excluded, rather than contaminating a single merged OCR result. A photo with two *separate* boxes that are each cleanly numeric but disagree (genuine ambiguity) still correctly returns `null` rather than guessing between them.
- **Tested against the real 4 reference photos — 2 real bugs found and fixed**: the user dropped the actual reference photos into `scratch/price-ocr-samples/` (gitignored, never committed) along with a ready-made test script (`scratch/test-price-ocr.ts`, kept as-is for anyone to rerun the same way — see "Local verification without LINE/webhook" below for how). Before that round's fixes, **0 of the 4 real photos** were recognized correctly (all returned `null`) despite 3 of them having large, unambiguous white price stickers — visually inspecting the actual crops (saved to disk via a throwaway debug script) found two distinct root causes: (1) real stickers have **rounded corners**, so the ~8% crop padding occasionally pulled in a sliver of background at a corner, which Tesseract read as one stray non-letter symbol tacked onto the real digits (`"280 °"`, `"270 |"`) — the line-purity check required the *entire* line to be digits/commas, so this silently discarded an otherwise-correct reading. Fixed by stripping any character that isn't a letter, digit, or comma before the purity check (`extractNumericLineValue`) — a real description line still gets rejected exactly as before, since it still contains actual letters; only non-alphabetic noise is now tolerated. (2) One crop — a clean, isolated "280" on white with nothing else in it — made Tesseract's **default page-segmentation mode (PSM AUTO)** return completely empty text; testing every PSM value in isolation found PSM 11 (`SPARSE_TEXT`) reads it perfectly. Now retries the *same* crop once with PSM 11 only when the default PSM found zero lines (then resets PSM back to `AUTO` for the next crop) — deliberately kept as a fallback rather than the default, since PSM 11 is more prone to shattering a busier crop (e.g. the touching-stickers case) into misread fragments; confirmed via testing that switching to PSM 11 globally actually makes the touching-stickers photo *worse* (misreads `990` as `9290` as a clean-looking but wrong standalone line) — the targeted-fallback approach avoids that regression entirely. **Result: 3 of the 4 real photos now correctly recognized (280/270/280)**; the 4th (the exact "two touching white stickers, price + Chinese description merged into one connected region" case the multi-box support above was built for) still correctly returns `null` — in that specific photo, OCR reads the price digits fused with stray letters on the very same text line (not a separate line), which the line-purity rule correctly treats as too ambiguous to trust rather than guessing.
- **Two real bugs found and fixed building the original version** (both discovered via a synthetic sanity test built locally — see "Verification" below): (1) the crop pipeline originally called `sharp().greyscale()` before OCR "to help it read cleaner" — that actually made `tesseract.js` return empty text 100% of the time in this stack (`.greyscale()` outputs a single-channel PNG, which this version of `tesseract.js`/Leptonica silently fails to read); removed it, `.normalise()` alone is enough contrast boost and doesn't break anything. (2) `sharp` conflicted with the `sharp@0.34.5` Next.js already depends on internally (for `next/image`) — installing our own `^0.35.5` left two different `sharp` versions in the tree, which on Vercel's Node runtime produced `ERR_DLOPEN_FAILED: libvips-cpp.so.8.18.7` at request time (crashed the whole webhook with a `500`, not just the OCR call) even though a completely fresh, uncached `npm install` had run; fixed by pinning our `sharp` to the exact `0.34.5` Next already uses successfully in production, which dedupes to one copy (confirmed via `npm ls sharp --all`). See "Deployment notes" below for the full debugging trail — this is a real trap worth remembering for any future dependency that might also want `sharp`.
- **客人端數量/價格互動整組移除（this round）**：延續上一輪移除暱稱綁定的簡化方向，這輪把整個「傳照片之後」的對話互動都拿掉——客人現在只剩「傳照片」「我要匯款」「取消訂單」三件事，數量/價格完全交給後台人工處理。整組移除、不留殘餘半套邏輯：
  - 「好了」觸發詞/keyword group、`handleDoneCommand`，連帶原本的「單輪最多 10 張」上傳上限（`countPendingPhotos`、`photo_over_cap` 文案）——沒有「好了」批次顯示這個概念了，這個上限本來就只是為了限制一次顯示多少張；拿掉觸發點後如果繼續保留，會變成一個永遠無法解除的卡住警告，所以一併移除，不是半套殘留。`MAX_PHOTOS_PER_ROUND`（常數本身，值仍是 10）**沒有刪**，現在單純當作功能六取消訂單 Carousel 的批次大小在用，跟上傳無關
  - 數量確認清單本身：`buildOrderItemBlock`（縮圖+名稱+單價/數量文字+1/2/3/4/5+ 按鈕+「價格有誤」「刪除」按鈕的那個 item block）整支刪除；`applyQuantityUpdate`（1/2/3/4 按鈕 + 5+ 輸入數字共用的寫入函式）整支刪除；`carousel_sent_at` 欄位不再寫入/比對（欄位留著不用）
  - 「價格有誤」回報整套：`handlePriceDisputeSubmission`、`awaiting_price_dispute_for_order_id`（bot state 欄位，程式碼不再讀寫，DB 欄位留著）、`parsePriceAmount`
  - 清單上的「刪除」按鈕：`handleDeletePendingOrder`
  - 「數量正確」觸發詞/keyword group、`handleQuantityConfirmTrigger`、`quantity_locked_at` 鎖定判斷——`applyQuantityUpdate` 本身都刪了，鎖定判斷自然跟著消失；`quantity_locked_at` 欄位留著不用
  - `buildOrderListBubble`（把 item block 陣列組成一個 Flex bubble 的純容器函式）**沒有刪**——雖然原本唯一的呼叫者（`handleDoneCommand`）沒了，但功能五的匯款清單繼續沿用這支函式，所以留著

### 功能四：訂單確認後的通知 — **removed** (this round)

- Originally: `PATCH /api/backend/community/livestream-orders/[id]` fired exactly one LINE **push** (`sendLineUserText`) the first time `purchase_status` transitioned to `'bought'` on a row with a `line_user_id`, guarded by `confirmed_notified_at` so later edits never re-sent it. **This has been removed** — the user decided the notification wasn't needed, since it was the only action in this entire feature that counted against the LINE OA's monthly message quota.
- Current behavior: the `PATCH` route now does a plain database update and nothing else — no `before`-row lookup, no push, no `notified` field in the response. Marking a row 已購買 (individually or via 功能三's batch tool) is silent from the customer's side.
- `confirmed_notified_at` (the column that used to guard against re-sending) is **left in the table as-is** — not read, not written, no migration to drop it. Removing an unused column wasn't worth a schema change for this; it's simply dead weight in `community_livestream_orders` now.
- This means the feature has **zero push messages anywhere** — see the note at the top of this section.

### 功能五：自助匯款申報 (new this round)

Brand-new LINE conversation flow, same trigger/reply pattern as "我要下單" (功能一/二). Only ever touches `community_livestream_orders.payment_status` and the new `community_livestream_remittances` table — does **not** touch `community_orders`/`community_remittance_submissions` (that older table stores the *customer's own* bank account the money came from, for the separate 記事本 system; this feature stores "which of *this* system's orders a report is meant to reconcile", a different concern entirely).

- Trigger: the `remittance` keyword group (default `我要匯款`/`匯款申報`/`回報匯款`/`匯款`, loose substring match, backend-configurable — see "Configurable trigger keywords" above) — **no binding/approval gate anymore** (see 功能一 above), any LINE user can trigger this directly.
- On trigger, `handleRemittanceTrigger` queries that user's own `community_livestream_orders` where `payment_status = 'unpaid'` — **no longer checks for unrecognized prices (this round)**: the old "block the whole batch if any row has `unit_price is null`" check and its `remittance_unresolved` reply were removed entirely, since nothing calculates/displays money anymore, so there's nothing left to be "unresolved" about. Every unpaid row is listed regardless of whether its price was ever recognized.
- **純展示清單，完全不提金額 (this round)**: `buildRemittanceItemBlock` now builds one row per item showing only a thumbnail + product name — no unit price, no quantity, no subtotal, no buttons — joined into a single Flex bubble via the same shared `buildOrderListBubble` helper 功能二 already uses (that helper itself wasn't touched; only the item-block content got simpler). The reply is still **two messages**: `[Flex 商品清單 bubble, 文字：提醒已完成匯款後回報後 5 碼 + 收款資訊 (if 收款帳號設定 has anything saved, see 功能三 above)]` — **no longer mentions 應付總額**, since nothing is calculated.
- **State snapshot, order ids only (simplified this round)**: at trigger time, `community_line_bot_states.awaiting_remittance_last5` is set `true` and the exact `order_ids` are written into that same table's `remittance_order_ids` column — still a snapshot (so an order added/removed in the gap between listing and the customer's reply doesn't silently change what gets recorded), but **no longer snapshots an amount** (the `remittance_amount` bot-state column is no longer read/written — column left in place, unused, same "don't drop it, just stop touching it" convention as every other removed field this round).
- `handleRemittanceLast5Submission` validates the reply as exactly 5 digits (`parseAccountLast5`, `/^\d{5}$/`) — an invalid reply gets `請輸入正確的匯款帳號後 5 碼（純數字 5 碼）...` and the awaiting state is **not** cleared, so the customer can just retry. On a valid reply: inserts one row into `community_livestream_remittances` (`line_user_id`, `nickname`, `order_ids`, `account_last5`, `submitted_at`) — **no longer passes `amount` at all (this round)**, relying on the new `202610020001` migration that dropped the column's `not null` constraint, so omitting the field just writes `null`; updates all of those `order_ids`' `payment_status` to `confirming`, clears the bot state, and replies `已收到您的匯款回報，我們將盡快為您核對，感謝您！`. A DB failure on the insert also leaves the state intact so the customer isn't forced to re-trigger the whole flow just to retry the same 5 digits.
- **Admin side already handles `null` amount gracefully, no backend HTML change needed**: the 社群連線訂單 card's "客人回報後 5 碼 / 申報金額" banner (`lily-backend.html`) already renders `order.remittanceAmount === null ? '—' : storefrontMoney(order.remittanceAmount)` — this was already null-safe before this round (written defensively even though the column used to be `not null`), so every new `null`-amount remittance just shows "—" instead of a broken value. Nothing to fix here.
- Admin side: the reported last-5 shows on the order's card once `payment_status='confirming'` (功能三 above, no declared amount to show anymore); after the admin reconciles against the bank statement, they use 功能三's batch tool to flip the reconciled cards' 匯款狀態 to 已付款 in one action.
- Entirely reply-based like 功能一/二 — no push (功能四's push was removed entirely in an earlier round, see above; this flow was never affected by it either way since it only ever touched `payment_status`, not `purchase_status`).

### 功能六：自助取消訂單

Brand-new LINE conversation flow, same trigger/reply pattern as "我要下單"/"我要匯款". Only ever touches `community_livestream_orders` — a customer can only cancel their own **not-yet-purchased AND not-yet-in-payment** items, and cancelling means the row is gone (hard delete, no cancellation log/audit trail — explicitly deferred, not built this round).

- Trigger: the `cancel` keyword group (default `取消訂單`/`我要取消`/`取消`, loose substring match, backend-configurable — see "Configurable trigger keywords" above) — **no binding/approval gate anymore** (see 功能一 above), any LINE user can trigger this directly.
- `handleCancelTrigger` queries that user's own `community_livestream_orders` where `purchase_status = 'not_bought'` **and** `payment_status = 'unpaid'` (oldest first, capped at 50 like the other list-building flows) — **both conditions changed this round**: originally this only checked `purchase_status`, which meant a customer who had already self-reported a remittance (功能五, `payment_status` flipped to `confirming`) could still cancel an order the admin was actively reconciling against a bank statement. Now `payment_status` must also still be `unpaid`.
  - None found → replies `目前沒有可以取消的商品喔（已購買或已在匯款流程中的商品無法取消）。` and stops.
  - Otherwise builds a Flex Carousel (same batching as the cancel flow always used — groups of 10, up to 4 batches since one slot is used by the leading text message, so up to `MAX_REPLY_MESSAGES - 1` batches) of the cancellable rows only — **purely 照片＋商品名稱 (quantity display dropped this round)**: `CancellableOrderRow`/`buildCancelBubble` no longer select or render `quantity` at all, consistent with "數量/價格互動整組移除" (see 功能二 above) — each bubble just shows the photo + product name, with one red "取消這項" postback button (`action=cancel_order&order_id=...`). A leading text message is prepended, covering both non-cancellable reasons in one count: if the customer has any rows that are either `bought` or already past `unpaid`, it says `您已購買或已在匯款流程中的 N 項商品不會列在這裡，恕無法取消。以下是可以取消的商品：` (`N` = this user's total row count minus the cancellable count — cheaper than a second OR-condition query, and exactly equivalent since both queries share the same `line_user_id` scope); otherwise just `以下是您目前可以取消的商品：`.
- Tapping "取消這項" → `handlePostback`'s `cancel_order` branch → `handleCancelOrder`: re-reads that row scoped by **both** `id` and `line_user_id` (so a customer can't cancel someone else's order id even by guessing/replaying an old postback), re-checks `purchase_status === 'not_bought'` (defends against a race where the admin bought it in the meantime — replies `這項商品已經購買，無法取消。` if so), then re-checks `payment_status === 'unpaid'` (defends against a race where the customer submitted a remittance report in the gap between opening the cancel carousel and tapping the button — replies `這項商品已在匯款流程中，無法取消。`, deliberately different wording from the purchased-block message so the customer knows which reason applied), then calls the same `deleteLivestreamOrder` the backend's delete button uses, and replies `已為您取消「商品名稱」，感謝您的訂購！`. **This flow never had a `quantity_locked_at` check** (that concept only ever applied to 功能二's now-deleted quantity-confirmation screen) — nothing to remove here even though "拿掉鎖定限制" was requested defensively this round; `purchase_status`/`payment_status` remain the only two gating conditions, unchanged.
- No push anywhere in this flow — same reply-only design as the rest of the feature.

### Deployment notes: `sharp` and `tesseract.js` on Vercel

Real, deployment-breaking issues surfaced getting `price-ocr.ts` running on Vercel — worth remembering for any future dependency that touches native/WASM modules or `worker_threads`:

- **`sharp().greyscale()` silently breaks `tesseract.js` OCR in this stack.** The crop pipeline originally converted to greyscale before OCR "for cleaner contrast" — this made `tesseract.js` return empty text (0 confidence) on every image, no error thrown. Root cause: `.greyscale()` makes `sharp` output a single-channel PNG, which this version of `tesseract.js`/Leptonica fails to read correctly. Fix: dropped `.greyscale()` entirely — `.normalise()` alone gives plenty of contrast for a white-background/black-text price sticker and doesn't have this problem. Caught by building a synthetic local sanity test (see "Verification" below) rather than by the real reference photos, which weren't accessible in this environment.
- **Two different `sharp` versions in the tree crashed the whole webhook function on Vercel.** Next.js 16.1.6 already depends on `sharp@0.34.5` internally (for `next/image`). Installing our own `sharp@^0.35.5` left both versions installed side by side (`npm ls sharp --all` showed `next@16.1.6 > sharp@0.34.5` **and** a separate top-level `sharp@0.35.5`). On Vercel's Node runtime this produced `ERR_DLOPEN_FAILED: libvips-cpp.so.8.18.7: cannot open shared object file`, which crashed `/api/line/webhook` with a `500` on **every** request (not just image messages) — confirmed via `vercel logs`, and confirmed it wasn't a stale-build-cache artifact by forcing a genuinely fresh, uncached install (`vercel deploy --force`) and seeing the identical error. Also tried marking `sharp` as a Next.js `serverExternalPackages` entry (`next.config.ts`) first, since that's the commonly-cited fix for this exact error message online — it changed how the module was bundled (confirmed via the error message switching to reference an "external module" wrapper) but did **not** fix the crash, so that theory was wrong for this specific case; left the config change in anyway since it's still correct general guidance for native modules and doesn't hurt. The fix that actually worked: pinned our own `sharp` to the exact `0.34.5` Next.js already ships and uses successfully in production, which dedupes to a single copy — confirmed via `npm ls sharp --all` showing `sharp@0.34.5 deduped`, and confirmed on Vercel by `curl -X POST .../api/line/webhook` returning `401` (the expected "route alive, signature check working" response) instead of `500`.
- Practical takeaway: if any future dependency added to this repo also wants `sharp` (or another native/optional-binary package Next.js itself bundles), check `npm ls <package> --all` for version conflicts *before* assuming a clean Vercel deploy — a conflict here doesn't show up as a build failure, only as a runtime crash on whichever route happens to load the module.
- **`tesseract.js`'s worker thread crashed Production outright — a separate, later incident, full writeup in "Production incident" above.** Short version: `new Worker(path.join(__dirname, ...))` inside tesseract.js's own source computes a path that Turbopack's `__dirname` rewriting breaks post-deploy; `outputFileTracingIncludes` alone (despite confirmably including the right file bytes) did **not** fix it, since the problem was never about missing files. The fix needed `serverExternalPackages: ["tesseract.js", "tesseract.js-core"]` **plus** an explicit `workerPath` passed to `createWorker()` — matching the two independently-reported fixes on [naptha/tesseract.js#868](https://github.com/naptha/tesseract.js/issues/868). Practical takeaway: any package that spawns a `worker_threads.Worker` with a dynamically-computed entry path (not a literal `require()`/`import`) is at risk of this exact class of bug under Turbopack — check upstream issue trackers for "Next.js"/"Vercel"/"worker" before assuming a library "just works" in this environment, and don't trust a clean local build as proof — this bug reproduced 100% of the time on every real Vercel deploy while never once reproducing locally.
- Unrelated to the above but hit along the way: local `vercel deploy` failed outright with `EPERM: operation not permitted, lstat '...\.tmp-community-psycopg\psycopg'` — a stray, unrelated, permission-locked directory (looked like a Python `psycopg`/`tzdata` install, already listed in `.vercelignore` on disk but Vercel's local file walk still choked on it) sitting in the project root. Not created by this round's work; relocated it out of the project tree (`C:\Users\lily.deng\Desktop\_quarantined-tmp-community-psycopg`, not deleted — its own subfolders were themselves unreadable/undeletable, likely broken reparse points) with explicit user confirmation before touching it.

### Local verification of `price-ocr.ts` without LINE/webhook (new this round)

`recognizePriceFromPhoto(buffer)` can be exercised directly against real image files on disk — no LINE account, no webhook, no migrations needed, since it's a pure function that only touches `sharp`/`tesseract.js`. This is how the real reference photos got tested once they were finally available as files (`scratch/` is gitignored/vercelignored, safe to drop real photos into without them ever being committed or deployed):

- Drop sample images into `scratch/price-ocr-samples/` and reuse `scratch/test-price-ocr.ts` (reads every image in that folder, calls `recognizePriceFromPhoto`, prints filename/result/elapsed-ms) — kept in place for anyone to rerun the same way.
- This project has no `tsx`/`ts-node` installed, and `import "server-only"` (a Next.js build-time-only marker package that isn't a real npm package in `node_modules`) makes a plain `ts-node`/`tsx` run fail outside Next's own bundler. The workaround that works in this environment: (1) create a throwaway no-op shim at `node_modules/server-only/{package.json,index.js}` (`module.exports = {}`) so plain Node can resolve the import — delete it again afterward, never commit it; (2) transpile with the project's own `tsc` directly to plain CommonJS, preserving the relative folder structure so the script's own relative import keeps working: `npx tsc --module commonjs --target es2020 --esModuleInterop --skipLibCheck --ignoreConfig --rootDir . --outDir scripts/_tmp-ts-out scratch/test-price-ocr.ts src/lib/line/price-ocr.ts` (run via the PowerShell tool, not Bash — same long-standing environment quirk as every other `npx`/`tsc` call in this project); (3) copy `scratch/price-ocr-samples/` into the matching path under `scripts/_tmp-ts-out/scratch/` (the compiled script's `__dirname` resolves there, not back to the real `scratch/`); (4) `node scripts/_tmp-ts-out/scratch/test-price-ocr.js`.
- **The script will hang after printing every result and never exit on its own** — this is expected, not a bug: `recognizePriceFromPhoto` deliberately keeps its shared `tesseract.js` worker (a `worker_thread`) alive for reuse across warm serverless invocations in production, and a plain one-shot Node script has nothing else keeping the event loop busy once the results are printed, so the live worker thread is the only thing left holding the process open. Just stop the process once the output looks complete (or add a temporary `process.exit(0)` at the end of a copy of the script) — don't take this as a sign anything is broken.
- Delete `scripts/_tmp-ts-out/` and the `node_modules/server-only` shim afterward; `scratch/` itself needs no cleanup (already gitignored/vercelignored).
